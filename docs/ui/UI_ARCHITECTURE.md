# UI-архитектура Banking Shell

**Banking Shell** — PET-проект: интерфейс банковского приложения и контракт данных к нему. Настоящего банковского ядра нет **намеренно**: его можно подменить или не подключать вовсе.

Этот документ — точка входа в UI-спецификацию. Он связывает шесть уровней проектирования и фиксирует границу между интерфейсом и данными.
Реализации пока нет. Кода, компонентов, API и адаптеров на этом этапе не пишем (см. [ROADMAP](../../ROADMAP.md)).

## Слои интерфейса

```
Композиция экрана (слой C)      AUTH-01, PAY-04, …
   ├─ знает маршрут и флоу
   └─ вызывает хук фичи ─────►  хук фичи (usePayment, useAccounts, …)
        ↓ передаёт данные                 │
Семантические компоненты (слой B)         │ типы из API-контракта
   └─ знают смысл: платёж, счёт, OTP      ▼
        ↓                          Интерфейс адаптера (уровень 6)
Примитивы (слой A)                        │
   └─ только отображение          DemoAdapter | NullAdapter | …
```

### Границы логики

| Слой | Что знает | Чего не знает |
|---|---|---|
| Примитив | Как нарисовать поле, кнопку, строку | Ничего о банке |
| Семантический компонент | Смысл: сумма, получатель, статус, намерение `confirm` | На каком он экране; откуда данные |
| Композиция экрана | Какие компоненты собрать; куда вести дальше | Как устроен адаптер |
| Хук фичи | Какой метод адаптера вызвать; состояние запроса (TanStack Query) | Как это нарисовано |
| Адаптер | Откуда данные: JSON, «ничего» или реальный банк | Что есть интерфейс |

**Бизнес-правила** («хватает ли денег», «верен ли MPIN», «лимит превышен») решает **только адаптер**. Результат возвращается как статус или ошибка из контракта. Интерфейс их показывает, но не вычисляет.

Это соответствует слоям data → domain ← ui из [R60](../../refs/README.md). Но отдельный доменный слой **не вводим**, пока не появится логика, которой нет места ни в адаптере, ни в хуке фичи.

## Уровень 5 — API-контракт: частичный старт

По [D-07] контракт пишется сейчас, но только для устойчивого ядра. В контракт попадает лишь то, что нужно экранам и флоу этой спецификации. Здесь — рамки первой части; эндпоинтов, типов и форматов здесь нет, они появятся в самом контракте.

**Правила:**

1. Предложения `[A]` на экранах с содержимым SOURCE_REQUIRED (Q-11) в контракт **не переносятся**.
2. Возможности устройства — SIM, биометрия, камера — в банковский контракт **не входят** [D-14].
3. MPIN — ровно 4 цифры [D-09].
4. У OTP есть назначение: онбординг или чувствительная операция [D-10].
5. Подтверждение платежа передаёт способ — биометрия или MPIN [D-13]. Биометрию проверяет граница устройства; в контракт уходит только способ и результат.

| Раздел | Данные для чтения | Действия | Экраны | В первой части |
|---|---|---|---|---|
| Сессия и вход | — | Вход по MPIN; вход после проверки биометрии на устройстве; выход | AUTH-01, SET-01 | Да |
| Регистрация | — | Регистрация по телефону; отправка полей AUTH-05 [D-15]; установка MPIN; запрос и проверка OTP (онбординг) | AUTH-02, AUTH-05…07 | Да, кроме подтверждения почты и согласий (Q-27) и полей карты для нового клиента (Q-26) |
| Счета | Счёт: название, маскированный номер, баланс, статус — в объёме `AccountCard` | — | HOME-01 [A] | Да. Реквизиты счёта (ACC-01) — нет, SOURCE_REQUIRED |
| Операции | Последние N операций: название, дата, сумма, статус | — | ACC-02; HOME-01 [A] | Да. Подробная выписка (ACC-03) — нет, SOURCE_REQUIRED |
| Платежи | Лимиты суммы; найденный получатель; комиссия [A] | Проверить получателя, подготовить платёж, подтвердить платёж | PAY-04, PAY-06, PST-01, PST-02 | Да. PAY-01 и PAY-02 — нет, SOURCE_REQUIRED. Формат данных QR (PAY-03) — UNKNOWN |
| СБП | Банки получателя по номеру телефона; выбран ли этот банк банком по умолчанию | Сделать банком по умолчанию [D-06] | PAY-04, SBP-03 | Да. SBP-02 — нет, SOURCE_REQUIRED |
| Настройки | Текущий язык | Сменить MPIN после OTP (чувствительная операция); сменить язык | SET-02, SET-04 | Да. Список языков — Q-17 |
| Карты | — | — | CARD-01 | Нет: содержимое UNKNOWN (Q-28) |
| Открытие счёта | — | — | ACC-07 | Нет: Q-26 |
| Уведомления, поиск, профиль, оплата услуг, отделения | — | — | NOTIF-01, HOME-02, HOME-03, PAY-02, SVC-03 | Нет: SOURCE_REQUIRED (Q-11) |
| Отключённые пункты | — | — | ACC-04…06, SVC-01, SVC-02, SVC-04 | Нет: [D-11] |
| Кредитная карта, кешбэк, накопления | Зарезервировано [D-05] | Зарезервировано | `CREDIT-xx`, `CASHBACK-xx`, `SAVE-xx` | Нет: место в контракте оставлено, проектируются отдельно |

## Уровень 6 — граница адаптера (только граница)

Реализация адаптеров **вне рамок этой задачи**. Здесь зафиксировано только, где проходит граница.

| Адаптер | Что делает | Связь с ROADMAP |
|---|---|---|
| `DemoAdapter` | Отдаёт демо-данные из JSON-файлов. Изменения хранит так, как решим в вопросе 3 ROADMAP (в памяти или в хранилище браузера) | «JSON-адаптер» |
| `NullAdapter` | Банковского ядра нет: чтение возвращает пусто, любое действие — ответ «недоступно». Интерфейс показывает `StatusMessage(kind=unavailable)` | Новый. Доказывает, что UI работает без ядра |
| `FutureRealBankAdapter` | Подключение к настоящему API | «HTTP-адаптер». Вне scope |

**Правила границы:**

1. Интерфейс импортирует только **типы контракта**. Конкретный адаптер интерфейс не импортирует никогда.
2. Какой адаптер работает, выбирается **в одном месте** конфигурации.
3. Замена адаптера **не меняет** ни одного компонента и ни одной композиции экрана.
4. На каждый метод контракта у `NullAdapter` есть осмысленный ответ. Значит, каждому экрану нужно состояние «недоступно».
5. **Возможности устройства** (SIM, биометрия, камера) — это не банковское ядро. У банковского контракта нет методов для SIM и биометрии; экран через хук фичи обращается к двум границам [D-14].

### Граница возможностей устройства [D-14]

Отдельная граница от банковского адаптера. Реализация — `DemoDeviceAdapter`; реализация тоже вне рамок этой задачи.

| Возможность | Где нужна | Демо-реализация |
|---|---|---|
| Выбор SIM | AUTH-03 | Демо-список SIM [D-03] |
| Привязка SIM | AUTH-04 | Демо-результат [D-03] |
| Доступность биометрии | AUTH-01, AUTH-06, SET-03, PST-01 | WebAuthn или демо |
| Проверка биометрии | AUTH-01, PST-01 | WebAuthn или демо |
| Камера для QR | PAY-03 | Браузерный API камеры, только HTTPS |

## Против раздувания

Это PET-проект. Всё перечисленное ниже **не вводится**, пока не появится явная необходимость:

- микросервисы, шина событий, Kubernetes;
- CQRS, распределённые транзакции;
- реальный KYC, интеграции с настоящими банками;
- отдельный доменный слой, фабрики адаптеров, внедрение зависимостей через контейнер;
- компоненты «на всякий случай»: `Avatar` отложен до появления экрана, где он нужен; `RecipientSelector` не входит в v1 [D-12].
