# UI-архитектура Banking Shell

**Banking Shell** — PET-проект: интерфейс банковского приложения и контракт данных к нему. Настоящего банковского ядра нет **намеренно**: его можно подменить или не подключать вовсе.

Этот документ — точка входа в UI-спецификацию. Он связывает шесть уровней проектирования и фиксирует границу между интерфейсом и данными.
Реализации пока нет. Кода, компонентов, API и адаптеров на этом этапе не пишем (см. [ROADMAP](../../ROADMAP.md)).

## Слои интерфейса

```
Композиция экрана (слой C)      AUTH-01, PAY-04, …
   ├─ знает маршрут и флоу
   └─ вызывает хук фичи ─────►  хук фичи (usePayment, useAccounts, …)
        ↓ передаёт данные                 │
Семантические компоненты (слой B)         │ типы из API-контракта
   └─ знают смысл: платёж, счёт, OTP      ▼
        ↓                          Интерфейс адаптера (уровень 6)
Примитивы (слой A)                        │
   └─ только отображение          DemoAdapter | NullAdapter | …
```

### Границы логики

| Слой | Что знает | Чего не знает |
|---|---|---|
| Примитив | Как нарисовать поле, кнопку, строку | Ничего о банке |
| Семантический компонент | Смысл: сумма, получатель, статус, намерение `confirm` | На каком он экране; откуда данные |
| Композиция экрана | Какие компоненты собрать; куда вести дальше | Как устроен адаптер |
| Хук фичи | Какой метод адаптера вызвать; состояние запроса (TanStack Query) | Как это нарисовано |
| Адаптер | Откуда данные: JSON, «ничего» или реальный банк | Что есть интерфейс |

**Бизнес-правила** («хватает ли денег», «верен ли MPIN», «лимит превышен») решает **только адаптер**. Результат возвращается как статус или ошибка из контракта. Интерфейс их показывает, но не вычисляет.

Это соответствует слоям data → domain ← ui из [R60](../../refs/README.md). Но отдельный доменный слой **не вводим**, пока не появится логика, которой нет места ни в адаптере, ни в хуке фичи.

## Уровень 5 — API-контракт: частичный старт

По [D-07] контракт пишется сейчас, но только для устойчивого ядра. В контракт попадает лишь то, что нужно экранам и флоу этой спецификации. Здесь — рамки первой части. Сам контракт с происхождением каждого поля — [API_CONTRACT_V1.md](../api/API_CONTRACT_V1.md).

**Правила:**

1. Предложения `[A]` на экранах с содержимым SOURCE_REQUIRED (Q-11) в контракт **не переносятся**.
2. Возможности устройства — SIM, биометрия, камера — в банковский контракт **не входят** [D-14].
3. MPIN — ровно 4 цифры [D-09].
4. У OTP есть назначение: онбординг или чувствительная операция [D-10].
5. Подтверждение платежа передаёт способ — биометрия или MPIN [D-13]. Биометрию проверяет граница устройства; в контракт уходит только способ и результат.
6. Подтверждение почты кодом из письма — отдельная операция регистрации, а не разновидность OTP [D-19].
7. Регистрация передаёт `onboarding_context: existing_customer | new_customer` [D-18]. Это контекст регистрации, а не ID экрана и не отдельный эндпоинт. Его определяет флоу по выбранной на AUTH-01 ссылке; от него зависит, есть ли в данных AUTH-05 поля карты. Компоненты контекст не определяют.
8. Запрос операций и перевод всегда называют конкретный счёт: `accountId` [D-23], `sourceAccountId` [D-24]. Заблокированный счёт счётом списания быть не может [D-25]. Счёта по умолчанию нет; какой счёт выбран — состояние флоу, а не компонента и не настройка.

| Раздел | Данные для чтения | Действия | Экраны | В первой части |

## Уровень 6 — граница адаптера (только граница)

Реализация адаптеров **вне рамок этой задачи**. Здесь зафиксировано только, где проходит граница.

| Адаптер | Что делает | Связь с ROADMAP |
|---|---|---|
| `DemoAdapter` | Отдаёт демо-данные из JSON-файла (`demo/seed.json`). Изменения хранит в `localStorage` браузера [D-27]; без браузера — в памяти | «JSON-адаптер» |
| `NullAdapter` | Банковского ядра нет: чтение возвращает пусто, если у ответа есть пустое значение, иначе «недоступно»; любое действие — ответ «недоступно». Интерфейс показывает `StatusMessage(kind=unavailable)` | Новый. Доказывает, что UI работает без ядра. Ничего не хранит и не ходит в сеть [D-27] |
| `FutureRealBankAdapter` | Подключение к настоящему API | «HTTP-адаптер». Вне scope |

**Правила границы:**

1. Интерфейс импортирует только **типы контракта**. Конкретный адаптер интерфейс не импортирует никогда.
2. Какой адаптер работает, выбирается **в одном месте** конфигурации: корень композиции `src/main.tsx`, переменная `VITE_BANKING_ADAPTER` (`demo` или `null`) [D-28].
3. Замена адаптера **не меняет** ни одного компонента и ни одной композиции экрана.
4. На каждый метод контракта у `NullAdapter` есть осмысленный ответ. Значит, каждому экрану нужно состояние «недоступно».
5. **Возможности устройства** (SIM, биометрия, камера) — это не банковское ядро. У банковского контракта нет методов для SIM и биометрии; экран через хук фичи обращается к двум границам [D-14].

### Граница возможностей устройства [D-14]

Отдельная граница от банковского адаптера. Интерфейс — `DeviceCapabilityAdapter`, реализации — `DemoDeviceAdapter` и `NullDeviceAdapter` (`src/adapters/device/`). Реализованы биометрия [D-31] и SIM [D-34]; камера — позже. Граница изолирует возможности платформы: в веб-демо они имитируются, нативная сборка может дать свою реализацию без правок экранов. Включён ли вход по биометрии — не возможность устройства, а настройка приложения [D-33].

| Возможность | Где нужна | Демо-реализация |
|---|---|---|
| Выбор SIM | AUTH-03 | `getSimCards()` — демо-список из 0, 1 или 2 SIM [D-03, D-34] |
| Привязка SIM | AUTH-04 | `bindSim(simId)` — демо-результат [D-03, D-34] |
| Доступность биометрии | AUTH-01, AUTH-06, SET-03, PST-01 | `isBiometricAvailable()` — демо [D-31]; WebAuthn — позже |
| Проверка биометрии | AUTH-01, PST-01 | `verifyBiometric()` — демо [D-31]; WebAuthn — позже |
| Камера для QR | PAY-03 | Браузерный API камеры, только HTTPS |
